# Backend корпоративной парковки, КР3

Spring Boot 3.5.5, Java 21, Spring Data JPA, PostgreSQL, Flyway, Spring Security, JWT, Swagger.
Веб-интерфейс написан на React. Страницы и стили находятся в `frontend/src`.

## Запуск

Из корня всего проекта:

```powershell
.\run.cmd web
```

Откройте http://localhost:8080. Данные первого администратора находятся в `.local/backend-login.txt`.
При первом входе смените временный пароль. Нужны заглавная и строчная буквы, цифра, специальный символ,
от 12 символов и не более 72 байт UTF-8. Пароль не должен содержать имя учётной записи.

Скрипт использует локальные JDK и Maven из `.tools`, при необходимости устанавливает их существующим `project.ps1`.
Maven скачивает Node.js для сборки, собирает React и включает его в JAR.
Скрипт запускает БД, сохраняет первоначальную резервную копию и запускает backend в Docker.
Dockerfile упаковывает уже собранный `target/parking-backend-1.0.0.jar`.

При ручном запуске сначала создайте `.env` по `.env.example`, затем:

```powershell
mvn -f backend/pom.xml clean package
docker compose --env-file .env --profile web up -d --build --wait
```

В `.env` укажите пароль существующей БД. Смена `DB_PASSWORD` не меняет пароль в уже созданном томе PostgreSQL.
Обычный `docker compose down` сохраняет данные. Не используйте `down -v` для рабочей базы.

### Разработка в IntelliJ IDEA

Запустите PostgreSQL из корня проекта командой `docker compose --env-file .env up -d --wait db`.
Откройте `backend/pom.xml` как Maven-проект, выберите JDK 21 и запустите `ParkingBackendApplication`.
В конфигурации запуска укажите корень репозитория как рабочую папку и добавьте аргументы:

```text
--spring.config.import=file:./.env[.properties] --server.address=127.0.0.1 --server.port=8081
```

Для разработки клиента с автообновлением запустите из корня проекта (потребуется Node.js 24):

```powershell
npm.cmd --prefix backend/frontend ci
npm.cmd --prefix backend/frontend run dev
```

Откройте http://127.0.0.1:5173. Vite отправляет запросы к API на порт 8081. Для другого адреса backend задайте `PARKING_API_URL` перед запуском Vite.
Можно также выполнить `npm.cmd --prefix backend/frontend run build` и открыть готовый клиент прямо на http://127.0.0.1:8081.

Адреса:

| Адрес | Назначение |
|---|---|
| `/` | Веб-интерфейс |
| `/api` | REST API |
| `/swagger-ui.html` | Swagger, только администратор |
| `/v3/api-docs` | OpenAPI, только администратор |
| `/actuator/health` | Состояние приложения и соединения с БД |

Порты публикуются на `localhost`: backend 8080, PostgreSQL 5433.
Правила дат и срочности в контейнере используют московское время.

## Как читать код

Начните с `controller/BookingController.java`, затем откройте `service/BookingService.java`
и `repository/BookingRepository.java`. Цепочка одного запроса:

```text
React -> REST-контроллер -> сервис -> JPA-репозиторий -> PostgreSQL
```

| Пакет | Что делает |
|---|---|
| `controller` | Принимает HTTP-запросы и проверяет роли |
| `dto` | Описывает входные и выходные данные, проверяет поля |
| `service` | Выполняет правила парковки и управляет транзакциями |
| `domain` | Описывает таблицы и статусы |
| `repository` | Читает и сохраняет сущности через JPA |
| `filter` | Собирает условия поиска из заранее известных полей |
| `security` | Проверяет JWT, пароли и текущего пользователя |
| `error` | Возвращает единый JSON ошибок |
| `config` | Настраивает безопасность, OpenAPI и первого администратора |
| `web` | Присваивает запросу correlation ID |

Контроллеры возвращают DTO, JPA-сущности наружу не передаются.
React отправляет запросы в `/api` и обновляет страницу по ответу. Spring Boot раздаёт собранный клиент и обрабатывает REST API.
`AuditedVersionedEntity` содержит общие даты и `@Version`, без универсальных CRUD-контроллеров.
В `BulkService` каждое действие получает отдельную транзакцию, поэтому ошибка одной брони не отменяет остальные.

## Данные и миграции

| Миграция | Изменение |
|---|---|
| V1 | Схема employees/bookings из КР1, с CREATE IF NOT EXISTS |
| V2 | Пользователи, роли, refresh-сессии, аудит |
| V3 | UUID, номера брони, архив, версии, теги, заметки, дополнительные поля и индексы |

Flyway принимает существующую схему как версию 0. Hibernate только проверяет структуру (`ddl-auto: validate`).
Существующие ID и связи сохраняются. Начальные номера старых броней имеют вид `B-1`, `B-2`.
Таблицы, не относящиеся к backend, например `entries`, миграции не удаляют.

UUID применяется в REST API. Числовой `legacyId` сохранён для КР1 и КР2.
PostgreSQL автоматически заполняет UUID, номер и даты при вставке из старого JDBC-клиента.
Триггеры увеличивают версию и меняют дату обновления при записи из любого клиента.
Уникальные индексы учитывают активный статус и отсутствие архива.

Перед первым запуском сохраняется `.local/parking-before-kr3.dump`. Для восстановления сначала остановите клиентов
и восстановите эту копию в отдельную базу через `pg_restore`, чтобы проверить содержимое перед заменой рабочей базы.

## Правила парковки

- Есть 50 мест с номерами от 1 до 50
- Сотрудник может иметь одну активную бронь на дату
- Одно место может иметь одну активную бронь на дату
- Новая бронь имеет статус `CREATED`
- Переходы: `CREATED -> CONFIRMED/CANCELLED`, `CONFIRMED -> COMPLETED/CANCELLED`
- Завершённые и отменённые брони нельзя редактировать
- Новую бронь нельзя создавать на прошедшую дату, будущую нельзя завершать
- Просроченную бронь можно отменить
- Архивирование освобождает место, восстановление проверяет конфликты
- Справочник сотрудников изменяет только администратор; отключение сохраняет историю
- Заметки видны всем вошедшим, изменяет автор с правом редактирования или администратор

`guest` означает гостевой визит. `spot` является числовым показателем: фильтр поддерживает `eq`, `gt`, `gte`, `lt`, `lte`.
Средний номер места выводится для обязательной числовой аналитики; занятость и свободные места сегодня помогают в работе.
В сводке `active` означает все записи вне архива, `open` означает действующие CREATED/CONFIRMED вне архива.

Вычисляемая срочность `urgency`:

| Условие | Значение |
|---|---|
| Неархивная CREATED на прошедшую дату | OVERDUE |
| Неархивная CREATED на сегодня или завтра | SOON |
| Остальные | NORMAL |

Показатель вычисляется при чтении и в SQL-фильтре, поэтому не устаревает при смене даты.

## API

| POST | `/api/bookings/{uuid}/restore` | Восстановление |
| DELETE | `/api/bookings/{uuid}/permanent` | Окончательное удаление из архива администратором |
| POST | `/api/bookings/bulk` | Массовое действие |
| GET | `/api/bookings/export` | CSV текущего фильтра |

| POST | `/api/bookings/import/apply` | Применение проверенного файла |
| GET, POST | `/api/bookings/{uuid}/notes` | История и создание заметки |
| PUT, DELETE | `/api/bookings/{uuid}/notes/{noteUuid}` | Изменение и удаление заметки |
| GET, POST | `/api/employees` | Справочник и создание сотрудника |

| GET | `/api/analytics/summary` | Сводка по всей базе |
| GET, POST | `/api/admin/users` | Список и создание пользователей |
| PUT | `/api/admin/users/{uuid}` | Изменение имени, почты, ролей, активности |
| POST | `/api/admin/users/{uuid}/reset-password` | Установка временного пароля |
| GET | `/api/admin/audit` | Поиск по аудиту |

Для `PUT` передайте `version` последнего ответа. Для архивирования и окончательного удаления передайте
`?version=...`, для восстановления JSON `{"version": ...}`. Устаревшая версия даёт HTTP 409.

Список принимает `q`, `employeeId`, `status`, `guest`, `urgency`, `tag`, `archived`, `spot`, `spotOp`, `from`, `to`.
Пагинация: `page` от 0, `size` от 1 до 100. Сортировка: `date`, `spot`, `code`, `employee`, `status`, `updated`,
например `sort=date,desc`. Все фильтры работают до пагинации на сервере.

Массовые действия: `ARCHIVE`, `RESTORE`, `STATUS`, `ADD_TAG`, `REMOVE_TAG`.
Тело: `{"ids":["uuid"],"action":"ADD_TAG","tag":"гость"}`. В ответе отдельные `successful` и `errors`.

## Авторизация

`VIEWER` читает данные, заметки, аналитику и экспорт. `EDITOR` дополнительно меняет брони, заметки, запускает импорт.
`ADMIN` также управляет сотрудниками, пользователями, просматривает аудит и может окончательно удалить архивную бронь.

Вход через React выдаёт access JWT и refresh-cookie. Клиент держит access JWT в памяти и восстанавливает вход через refresh при перезагрузке.
Администратор из веб-интерфейса может открыть Swagger. Для вызовов REST API из Swagger нужен отдельный bearer-токен.
Роли и активность перечитываются из БД. Смена или сброс пароля отзывает refresh-сессии и делает прежние JWT недействительными.
Пять неверных попыток входа блокируют учётную запись минимум на 5 минут.

Клиенты REST API передают access JWT в заголовке `Authorization: Bearer ...`. Токен действует 15 минут.
Вход через API с `clientType: "WEB"` сохраняет refresh в HttpOnly/SameSite=Strict cookie.
Будущий Android-клиент использует `clientType: "NATIVE"` и получает refresh в JSON.
Обновление отзывает предыдущий refresh, выход из API отзывает refresh-сессию. Выданный access JWT действует до истечения своего срока.

Пароли хранятся как BCrypt-хеши, refresh-токены как SHA-256. В аудит не записываются пароли и токены.
Настольный клиент КР2 подключается к БД напрямую и работает отдельно от HTTP-авторизации КР3.

## CSV

UTF-8, разделитель запятая. Пример:

```csv
code,employeeEmail,spot,date,status,purpose,guest,tags
VISIT-001,anna@company.ru,12,2026-12-01,CREATED,Рабочий день,false,встреча|гость
```

Сотрудник должен быть добавлен заранее. Дату укажите актуальную.
`NEW_ONLY` отклоняет существующий номер, `UPSERT` обновляет по `code` с проверкой правил и версии.
Импорт не обходит запрет изменения закрытой или архивной брони.

Preview проверяет каждую строку тем же сервисом в откатываемой транзакции, запись и аудит не сохраняются.
Счётчики последовательностей PostgreSQL могут увеличиться при проверке, пропуски ID допустимы.
Результат привязан к пользователю, действует 15 минут, хранится в памяти до перезапуска сервера.
Apply использует `previewId`, применяет корректные строки по одной, возвращает ошибки отдельно.
Уже применённый preview повторно использовать нельзя. Перед записью правила и версии проверяются снова.

## Проверка и защита

```powershell
.\run.cmd web-test
.\run.cmd web-test-db
```

Первая команда проверяет Spring Context, HTTP API, роли, пароль, JWT, refresh, блокировку входа,
фильтры, версии, конфликты, архив, заметки, массовые действия и CSV на H2.
Вторая проверяет SQL-миграции, сохранение старых записей, триггеры и индексы на PostgreSQL.
Она создаёт и затем удаляет отдельную схему `parking_test_<uuid>`, рабочие таблицы не меняет.
Модульные тесты срочности и политики паролей находятся рядом.

Для защиты покажите по порядку: контейнеры и health, вход и роли, сотрудника, создание брони,
фильтры и страницы, изменение с версией, архив и восстановление, заметку, массовое действие,
CSV preview/apply/export, сводку, пользователей, аудит, Swagger и историю Flyway.

Авторизация и служебная структура адаптированы из учебного архива Student Hub, указанного в задании.
Модели, правила, API парковки, миграция прежней базы и веб-интерфейс реализованы для этого проекта.
